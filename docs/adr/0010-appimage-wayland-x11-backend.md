# 0010: AppImage 在 Wayland 会话下撤销 GDK_BACKEND=x11，规避 WebKitGTK 的 XIM 假死

issue #46 的现象是：Linux 下以 AppImage 运行，点任意输入框后整个应用假死——窗口不再重绘、键盘无反应，只有缩放窗口还能刷新出当前内容；同一台机器、同一用户用 `pnpm tauri:dev` 启动，以及 Windows 下的应用，都没有这个问题。先确认这不是「命令卡住」也不是「主循环被困住」：卡死现场取 core 后，UI 进程主线程停在 `gtk_main_iteration_do` → poll，即主循环仍在正常轮询，而窗口却不再出帧（缩放窗口能重绘），说明被掐断的是渲染/输入这条路径，不是某个 Rust 命令或锁。随后从运行中的 AppImage 进程取证，差异落在输入法路径上：出厂产物（从 Release 下载的 0.3.0 AppImage）的环境里 `APPIMAGE`/`APPDIR` 有值、`WAYLAND_DISPLAY=wayland-0`，同时 `GDK_BACKEND=x11`；它的 `maps` 里载入了 `…/usr/lib/gtk-3.0/3.0.0/immodules/im-xim.so`（XIM 输入法模块），窗口是 X 客户端（xdotool 可见），即被按 XWayland 跑。把同一份 AppImage 内容（挂载/解包后的目录，其余环境一字不改）去掉 `GDK_BACKEND` 再启动，进程持有 wayland fd、xdotool 找不到窗口、载入的是 `im-wayland.so`，启动日志与 `list_providers`/`list_plugins` 正常、界面正常渲染。换言之，AppImage 与 `tauri dev` 的唯一系统性差异就是「X11 后端」：Wayland 后端走 GTK 的 Wayland 输入法路径，X11 后端下 GTK3 又会因会话里存在 `XMODIFIERS`（fcitx5 等输入法会设置，本机为 `@im=fcitx`）而默认选用 XIM 模块，于是踩上 WebKitGTK 的 XIM 缺陷——输入框一获得焦点就不再出帧。这与外部报告吻合：kanriapp/kanri#961 描述「一旦打开需要输入的面板渲染就停止，缩放窗口才刷新」，并注明 Wayland 会话正常、把输入法从 XIM 换成 IBus 也正常；block/buzz#4854 描述 AppImage 配 `GDK_BACKEND=x11` 加 fcitx5 时「聚焦输入框正常，一打字整个应用冻结」，其临时规避是 `GTK_IM_MODULE=gtk-im-context-simple` 配 `XMODIFIERS=`。

`GDK_BACKEND=x11` 不是我们自己的配置，而是 AppRun 带来的：AppImage 的 AppRun 由 linuxdeploy 生成，只 source 一个固定文件名 `apprun-hooks/linuxdeploy-plugin-gtk.sh`（linuxdeploy-plugin-gtk 注入），该脚本无条件 `export GDK_BACKEND=x11`，注释写明是为绕开 tauri-apps/tauri#8541（老发行版上构建的 AppImage 在 Wayland 后端下撞 settings schema 缺键而崩）。Tauri 的 AppImage 配置只暴露 `bundleMediaFramework` 与 `files`，没有注入 AppRun 钩子的机制；`files` 虽然能往 AppImage 里塞任意路径，但 AppRun 只 source 上面那一个文件名，新增钩子文件不会被加载，而覆盖同名文件又要依赖「拷贝文件」与「linuxdeploy 生成该文件」的先后顺序，属于跟着第三方脚本内容长期走钢丝。

决策是让应用自己在启动最早期撤销这个覆盖：在 `run()` 开头、GTK/WebKit 初始化之前，当且仅当 `APPIMAGE` 有值、`WAYLAND_DISPLAY` 有值、且 `GDK_BACKEND` 恰好是 `x11` 时删除该变量，把后端选择交回 GDK。三个条件缺一不可——没有 `APPIMAGE` 说明不是 AppImage 启动（`tauri dev`、`.deb`/`.rpm` 安装版等），此时不该覆盖用户或环境的自选；没有 `WAYLAND_DISPLAY` 说明是 X11 会话，x11 后端本就是既有行为；值不等于 `x11` 说明是别的来源在指定，不动。删除而非改写为 `wayland`，一是效果等价（Wayland 会话下 GDK 本就优先 Wayland），二是少一处硬编码、X11 会话不受任何影响。代价与已知缺口有三项。其一，Wayland 会话下不再走 XWayland，绕开 tauri#8541 的那层保护在这条路径上消失；本次在本机与 AppImage 实际内容上验证了 Wayland 后端可正常启动、渲染并跑通命令，若将来某个发行版真的复现 schema 崩溃，需要另找办法而不是改回去（改回去等于恢复本 bug）。其二，纯 X11 会话完全不受影响，因此 WebKitGTK 的 XIM 缺陷在那种会话下依然存在——那是上游问题，且在不牺牲 CJK 输入法的前提下无法从应用侧规避，本 ADR 不承担它。其三，无法区分「钩子写死的 x11」与「用户自选的 x11」，所以 AppImage + Wayland 下显式指定 x11 的用户也会被改掉；因为这是把钩子写死的默认值收回，本次不为此加开关。

曾考虑并否决的形态：套用 buzz issue 的规避（`GTK_IM_MODULE=gtk-im-context-simple` 配 `XMODIFIERS=`），代价是 CJK 输入法整体失效，不能作为产品修复；自己投放 `apprun-hooks/*.sh`（AppRun 只 source 固定文件名，不会被加载）；用 `bundle.linux.appimage.files` 覆盖 `apprun-hooks/linuxdeploy-plugin-gtk.sh`（依赖生成与拷贝的先后，且要跟随第三方脚本内容）；让 AppImage 不捆绑 GTK/WebKit 改用系统库（Tauri 未暴露该开关，且捆绑本身还顺带覆盖「用户没装 webkit2gtk-4.1」的场景）；把 `GDK_BACKEND` 改写为 `wayland` 而非删除（更硬编码，且对 X11 会话会多出无意义的分支）。修复的验证限于「不再走 X11/XIM 路径」这一层：五组环境组合（AppImage+Wayland+钩子强制的 x11、非 AppImage+Wayland+x11、AppImage+纯 X11+x11、AppImage+Wayland+`wayland`、AppImage+Wayland 未设该变量）逐一实测了后端与载入的输入法模块，出厂 AppImage 内容也做了同样的 before/after 实测。**「点击输入框不再假死」这一步未能自动验证**：本机的指针注入（`xdotool` 的 XWarpPointer）在该会话下被吞掉、合成键盘事件也未能驱动界面，因此这一条需要人工在真实 AppImage 上点击确认。
