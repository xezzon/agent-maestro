# 0016: 端点选择移交插件，WIT 合同升级至 2.0.0

ADR 0003 从建模第一天就允许 Provider 对两种协议各持一个端点（`base_url` 按协议分槽的 map），但界面用单选框强制二选一，于是「配置里有两个槽位」始终只是潜在状态。当时过渡方案的收口之处是把「投影用哪个端点」判给宿主：投影时 `select_endpoint` 按「唯一非空槽位」挑选，读不出唯一值时（端点为零或两个）把该 Provider 记入 `SkippedProvider`（ADR 0015 有记载）。#93 放开界面、允许两个端点同时录入后，这个「唯一非空」前提不再成立——宿主若继续挑选，就只能丢掉一个用户明确配置过的端点，或继续把双端点当成跳过。

我们决定**宿主只做映射、不做选择**：投影时宿主按固定顺序（`openai-completions` 在前）把 Provider 的非空端点收集成列表，连同界面记录的投影选择 `selected-protocol` 原样交给插件，由插件裁定实际使用哪个端点。选择规则落在插件侧（合同只约束输入的形状，不约束选择策略）：所选协议确有对应端点则用它；否则若只剩一个端点则用它；否则多端点且无有效选择时优先 `openai-completions`（固定顺序里的首选）。规则覆盖三类输入：旧配置未记录选择（走「唯一端点」分支）、选择指向后来被清空的协议（同前）、以及恰好两个端点都有而选择缺失（走首选兜底）——「选择有效」永远以「该协议的端点确实存在」为条件，选择本身不构成真理。

**投影选择只存协议名，不重复存 URL**。端点 URL 的唯一真相是 `base_url` 分槽 map；若把选中端点的 URL 一并落盘，就制造了第二份真相，两者可能各自漂移（改槽位忘改选择、或反之）。只存协议名则不存在同步问题——插件用协议名回查端点，查不到就按兜底规则处理，选择失效是良性的而非错误。字段设计为可缺省：`selected_protocol: Option<Protocol>` 以 `serde(default, skip_serializing_if = "Option::is_none")` 落盘，旧配置无此键时读为 `None`、写入时不产生该键，**无需配置迁移**。未选中的槽位由界面在整包保存时归一化为 `null` 送入插件，使「选择 ⊆ 已填槽位」成为命令层的稳定输入前提；但这个前提只在界面路径成立，配置可被手工编辑，插件仍须按「选择可能缺失或指向未配置协议」实现。

**零端点的 Provider 仍由宿主在映射层跳过**（原因「未配置任何协议端点」），不进入 `providers` 列表。理由有三：其一，WIT 的 `write-providers` 返回 `result<list<string>, string>`，没有逐 Provider 的跳过通道，零端点条目进入列表后插件无法把「跳过」回传投影报告；其二，零端点是 ADR 0015 认可的合法配置状态（占位符可解析为空串），与插值的**错误**不同类，不应让插件去辨别；其三，插件是整文件重写，逐条判断「该不该跳过」没有收益，只会把宿主的职责边界扩散到每个插件。这条通道保留在宿主，是宿主**映射**职责的一部分，与「不做选择」不矛盾：宿主决定谁进入列表（结构过滤的一致性），插件决定进入者用哪个端点（选择策略的适配性）。

**WIT 合同升 2.0.0 是 breaking 变更**：`provider` record 的字段形状被替换——删去标量 `protocol`/`base-url`，改为 `endpoints: list<endpoint>`（`endpoint` 是新增的 `{ protocol, base-url }` record）与 `selected-protocol: option<protocol>`。旧字段名被移除且语义由「单端点」变为「端点列表 + 选择」，任何按旧形状读写的插件都无法编译，故按 major 号升级而非 minor。按 ADR 0013 收回的承诺，宿主只注册当前包版本的导出（`maestro:plugin/plugin@2.0.0`），旧合同组件在宿主侧链接失败、须以新版 SDK（同步升 2.0.0）重编译；生态当前只有内置 pi，重编译成本即改一处插件。SDK 版本对齐约定（SDK 2.x ↔ WIT 2.x）随之上移。

曾考虑并否决的形态：宿主继续挑选（挑「第一个非空槽位」或「优先 openai」）——丢弃用户已经做出的选择，与「配置以 Maestro 为准」矛盾，且把「哪个协议更适合某工具」的知识错放在宿主；宿主把双端点继续当作 `SkippedProvider`——正是 #93 要废除的旧行为；把选中端点的 URL 与选择一起落盘——制造第二份真相与漂移风险，见上；不引入 `selected-protocol`、只靠「唯一端点 / 首选」兜底——当两个端点都配置时无法表达「我就是要用 anthropic」，用户的意图无处安放；把选择建成「槽位索引」或直接存端点对象——索引与列表顺序耦合、端点对象重复存 URL，都不如协议名稳定；零端点也送进插件让插件跳过——见上三条理由，宿主的映射层是更合适的收口处。
