# 0009: Release 仅由手动触发，缓存拆为共享 cargo home 与按 profile 各自的 target

`.github/workflows/` 下的两条流水线原本共用一套缓存约定：键为 `<os>-<arch>-cargo-<Cargo.lock 哈希>`，路径把 `~/.cargo/{bin,registry,git}` 与 `src-tauri/target/`（外加宿主 build.rs 就地编译的内置插件 wasm 的 target）一起打包，Release 则由 `push` tag 触发（#54）。这套约定有三处结构性缺陷。其一，缓存的作用域跟着运行所在的 ref 走：tag 运行只能读默认分支的缓存，写出的条目只属于该 tag。改造前的现场证据是一次从临时分支 `probe-54` 发起的 Release 实验，它产出的 4 条 release 产物条目全部落在 `refs/heads/probe-54` 作用域，其它 tag 与 main 都读不到。其二，Check 存的是 dev profile 产物，Release 要的是 release profile 产物，两者在 target 目录里互不通用；而 `actions/cache` 在主键精确命中时会跳过保存，于是同一个键下先跑的一方会把另一方的产物永久挡在缓存之外——tag 运行从 main 恢复到的缓存只省下了依赖下载，编译仍要全量重来。其三，键里只有 `Cargo.lock` 哈希：工具链（`rust-toolchain.toml`）变更而依赖不变时，旧产物被恢复、rustc 变化导致全部重编、保存又因精确命中被跳过，此后每次运行都陷入同样的全量重编。配额同时已经见底：改造前 11 条缓存合计约 12.5 GB，超过仓库 10 GB 上限、LRU 驱逐已在发生；其中两条同键的 2.77 GB 条目分别落在 main 与一个已合并 PR 的 merge ref 上——后者 main 读不到，main 的推送只能从更旧的键部分恢复后再编一遍。

决策有三项。其一，Release 删除 tag 触发、只保留 `workflow_dispatch`：缓存的读写都落在 main 作用域，release profile 的产物才能在两次发布之间复用。代价是发布动作从「推 tag」变为「在 main 上手动运行」，且 tag 由 tauri-action 在 dispatch 的那个 commit 上创建（`tagName: v__VERSION__`），因此「同一版本号重发」需要先删 tag 或让版本号前进——本次不为它加机制，按 tauri-action 的默认行为处理。其二，Release job 绑定 GitHub 环境 `release` 作为分支守卫（配置在仓库设置里，不在版本控制内）：自定义分支策略只允许 `main`、不配 reviewers、并关闭 admin 绕过（`can_admins_bypass: false`，否则仓库 admin 的操作不受该策略约束，守卫形同虚设）。其三，在不引入第三方 action 的前提下重排缓存：cargo home（`~/.cargo/registry/{index,cache}`、`~/.cargo/git/db`）单独成键，且不带 os/arch 前缀、跨平台共享——registry 里是 `.crate` 源码包，与 rustc 版本和平台都无关，Check 在 main 上的推送持续续它的 TTL（7 天不访问即驱逐），各平台的 Release 都读它；代价是平台特有依赖（如 Windows 的 `windows-sys`）不会因此进入条目，每次仍要小额下载，且因精确命中不再回写，这个缺口不会被补上，属明知接受。跨 OS 恢复还需在两条缓存步骤上显式打开 `enableCrossOsArchive`（`actions/cache` 默认只允许恢复与创建时同 OS 的归档），否则「跨平台共享」只是键上的共享、Windows 实际永远读不到 Linux 写出的条目。产物则按 profile 分键（`cargo-test-` / `cargo-release-`），键里除 `Cargo.lock` 哈希外再加 `rust-toolchain.toml` 哈希，路径仍覆盖 `src-tauri/target/` 与 `plugins/pi/target/`。顺带去掉 `~/.cargo/bin/`：那是 rustup 管理的平台相关可执行文件，两条流水线都不往其中安装任何东西，而它所属的条目已经跨平台共享。

Check 侧的配套改动只有一项：job 级 `CARGO_INCREMENTAL: "0"`。CI 里增量编译没有收益——job 内 clippy 与 test 用不同驱动与参数、互不共享产物，跨运行又靠缓存——而它会在 `target/debug` 里留下可观的一块增量数据，拖慢每次缓存的恢复与保存。Check 的触发器保持不变（PR + push main + 手动）：main 上的推送正是 home 条目 TTL 的续命来源。

运维含义值得单列。环境必须先建好并配好分支策略、再合并工作流改动：工作流引用一个不存在的环境时 GitHub 会自动把它创建出来（一个没有任何规则的裸环境），守卫会静默失效且不报错。守卫的验证方式只有一种：从非 main 的 ref 手动触发一次，确认那个 job 被拒、且没有创建 tag——本次改造前该环境已在仓库设置中配好，这一步仍需在合并后实跑。发布流程相应变为：在 main 上手动运行（dispatch 时填入 `version`，它决定运行名）→ 工作流把该版本号写进 `tauri.conf.json` 并推送 main，随后在该提交上构建、建 tag `v__VERSION__` 并挂 draft release（版本号的写入方式见 [0012](0012-app-version-single-source.md)）→ 校验 draft 产物 → publish。缓存条目 7 天未被访问即被驱逐，而 release 产物条目只有发布时才会被碰，因此发布间隔超过一周时它会消失、下一次发布退化为全量冷编；改造后的第一次手动发布本来就必然冷编（当时世界上还不存在 release profile 的缓存），第二次起才见效。仓库配额方面，改造前已删除约 9.5 GB 陈旧条目：实验分支作用域的 4 条、已合并 PR 的 merge ref 1 条、已关闭尝试的 1 条、main 上旧 lock 的 1 条。

曾考虑并否决的形态：`Swatinem/rust-cache`（PR #70 已实现并实测：条目更小——Check 1.54 GB 对 `actions/cache` 的 2.77 GB、release 每平台 0.71–0.82 GB——且键天然含 rustc 版本与平台；否决理由是本次不引入第三方依赖）；在 main 上增加 release 预热 job 并保留 tag 触发（PR #70 的另一半设计，用一次额外的 release 构建换取 tag 运行可读的缓存；与「只保留手动触发」是同一问题的两条解法，选了后者）；cargo home 键带 os/arch 前缀（各平台一份完整条目，但只在发布时更新，7 天驱逐会实打实落在它们头上）；新增定时工作流只做缓存恢复以续 TTL；缓存 SDK crate（`crates/maestro-plugin-sdk`）的 target（它的 `Cargo.lock` 不纳入版本控制，键里只能放清单哈希，追不上每次重新解析出的依赖图）；apt 包缓存（实测每个 Linux job 省约 20–30 秒，需再引入第三方 action 并对 `/var/cache/apt` 做 sudo 操作）；用 `paths-filter` 跳过纯前端改动的 rust job（判定面宽，误判的代价是漏检）；用 job 级 `if: github.ref == 'refs/heads/main'` 做分支守卫（改为 GitHub 原生环境机制，守卫落在仓库设置而非每个需要它的 job 上）。

三处 GitHub 行为未能离线查证，实现时按假设处理并在首次运行时验证：tauri-action 在 tag 不存在时以 dispatch 的 commit 为落点创建 tag；环境的分支策略会让违规 job 失败而非静默通过；引用不存在的环境会被 GitHub 自动创建（这条已用「先建环境再合并」规避）。
