# 0002: API Key 存系统密钥链，配置只存 `secret://` 引用，单向写入

调用 Provider 需要凭证，README 承诺 API Key 仅存本地系统密钥链。我们决定：真实密钥只写入 OS 密钥链（macOS Keychain / Windows Credential Manager / Linux Secret Service），配置文件里 `api_key` 字段只保存两种值之一——null（未设置）或引用 URI `secret://io.github.xezzon.agent-maestro/provider/<slug>/api_key`；前端永不读回密钥本身（更新契约：`null`=不变、`{ slug, value }`=覆盖写入、`{ slug }`=清除）。

这是「单向写入（write-only）」姿态：渲染进程即使被攻破也拿不到密钥，只能看到无秘密的引用。为此拒绝了「显示/隐藏」回读密钥的常见 UX（每次渲染都把秘密送回前端，姿态明显更弱）。配置因此可移植、不含秘密；代价是密钥链条目与配置文件分离（整目录拷贝到新机器不会带走密钥链条目，留待同步功能处理）。

修订（2026-09-08）：第一期（#24）暂缓采纳本决策——`api_key` 以明文字符串直接存入配置文件，以收敛首期范围、避免密钥链在 Linux Secret Service 上的跨平台不确定性。本 ADR 的「密钥链 + `secret://` 引用」方案保留为目标状态，将来落地时需做一次数据迁移（明文值写入密钥链、替换为引用）。在此之前，配置文件以明文承载密钥是已知的、有意的取舍。

修订（2026-10-27，落地 #61）：目标状态落地，2026-09-08 的「暂缓」随之失效；本节取代上文的三态契约。落地后的决定：

- **真值只写入系统密钥链**，命名空间 `io.github.xezzon.agent-maestro`、account `provider/<slug>/api_key`。配置文件里的 `api_key` 只取三态：空串（未设置，取代上文所说的 `null`）、规范引用（已设置）、迁移失败时暂时保留的旧明文。新写入路径不产生明文。对应的类型是 `secret::SecretText`（`Unset | Ref(SecretRef) | Plaintext(String)`，通用的密钥字段三态）；`Debug` 仍只渲染 `<set>`/`<unset>`。
- **引用与明文在类型上可区分**。以 `secret://` 开头的值一律按引用处理；不符合规范的引用让整份配置进入保护态并点名 slug。`secret://` 是保留前缀，明文密钥不能以它开头。加载后逐条校验引用的 account 与 map key 推出的 slug 一致；slug 不可变，引用因此稳定。
- **线上三态契约改为**：`api_key` 缺省或 `null` = 不变；`""` = 删除密钥链条目并置空引用；其余非空字符串 = 覆盖写入并刷新引用；本 slug 的规范引用回传按「不变」处理，不产生新密钥。新建时缺省/空串都落为未设置，任何引用一律拒绝。
- **写入顺序先密钥链、后配置**。配置落盘失败按操作前的旧值回滚；回滚也失败时返回同时点名两次失败的错误，绝不写明文。删除 Provider 只在字段为引用时清理密钥链条目；`NoEntry` 在清除/删除中是幂等成功。密钥链不可用时保存与删除如实失败，配置不动。
- **启动时一次性迁移**：逐 Provider 把旧明文写入密钥链并替换为引用，全部尝试完只落盘一次；失败者保留明文、不阻塞启动、下次启动重试。迁移失败在界面以「明文待迁移」标记，并在日志中记 ERROR。
- **投影前一次性解析**待投影 Provider 的密钥（启用且会被投影者）。任一密钥缺失或密钥链不可用即让整个「应用到工具」失败，不进入逐插件流程；绝不把引用 URI 或空值交给插件。
- **配置版本升到 2**：读取接受 1 与 2；一旦落盘内容出现任何引用就写 v2，全部仍是明文的 v1 可暂时留在 v1；版本号不回退。这样旧版 Maestro（≤0.5.x）不会把引用当成 API Key 投影出去。
- **界面保持单向写入**：列表与表单只显示「已设置 / 未设置」，已设置时只提供「更换 API Key」（留空保存 = 清除），未设置时提供输入框；前端永不读回真值。
- **平台后端**由 `keyring` 提供：macOS `apple-native`、Windows `windows-native`、Linux `sync-secret-service`（`crypto-rust`、`vendored`）。不启用 keyutils；不支持的目标没有该依赖，编译期即失败。

接受的残余风险：两次写入之间崩溃/掉电会留下没有引用的孤儿密钥条目（惰性，同 slug 下次写入时覆盖）；迁移失败期间配置文件仍含旧明文，直到下次启动或用户重新设置；`secret://` 保留前缀与合法密钥冲突时拒绝该密钥；旧版 Maestro 遇到 v2 配置进入保护态，需升级后才能读写。

修订（2026-10-28，落地 #144）：`SecretText` 是**通用的密钥字段三态**，`Plaintext` 可自由构造——它为将来「密文 / 明文二者皆可」的字段准备，类型不替字段决定允不允许明文。API Key 的「只允许未设置 / 引用」是**字段级规则，落在写入路径上**：三态意图只映射出 `Unset` 或 `Ref`，明文只在读旧配置时出现，迁移路径（#147）把它换进密钥链后落引用。据此**不做**「落盘内容出现明文即拒写」的全量闸门：迁移失败时保留旧明文是刻意接受的（见上），把整份配置挡在门外只会丢掉密钥。

修订（2026-10-28，落地 #145）：写入链路落地，配置版本随之升到 2。

- **配置版本**：读取接受 1 与 2，更高版本进保护态；新配置从 2 开始；落盘内容一旦出现任何 `Ref` 即写 v2；全部仍是明文的 v1 暂留 v1；版本号永不回退（旧版 Maestro 见到 v2 会进保护态，回退等于让它又能把引用当明文用）。解析时逐条校验引用与其所在 map key 推出的 slug 一致，不一致整份配置进保护态。
- **线上三态契约**（命令层解析 `api_key` 载荷）：缺省 / `null` = 不变；`""` = 清除；本 slug 的规范引用 = 不变（防前端回传）；其它 `secret://` 前缀值一律报错、不进存储层；其余非空串 = 覆盖。新建时缺省与清除都落成未设置，任何引用（含规范引用）一律拒绝。
- **写入顺序**：永远先密钥链、后配置。覆盖先写条目再落引用；清除先删条目（不存在算成功）再落空串；删除 Provider 仅当字段为 `Ref` 时删条目，`Plaintext` / 未设置直接删记录、不碰密钥链。配置落盘失败按旧值恢复密钥链（旧值不存在就删掉新值），回滚本身也失败时返回同时点名两次失败的错误。
- **密钥链只在凭证真的被动时碰**：清除只在记录持有引用时才删条目——没有凭证的 Provider 保存不依赖密钥链可用，密钥链不可用时挂掉的只是「带密钥的保存」。
- **过渡态（已随 #146 作废）**：本票不含投影解析（#146）与启动迁移（#147），故「绝不把引用 URI 或空值交给插件」这一条在 #145 落地时**暂不成立**——投影把 `Ref` 暂按未设置传递（引用 URI 绝不交给插件，`Plaintext` / `Unset` 行为不变）。#146 落地后本段作废（见下节）。启动迁移（#147）仍待落地：旧明文配置继续以明文工作。

修订（2026-10-28，落地 #146）：投影前解析密钥落地，上一节记下的过渡态随之作废。

- **只读端口 `SecretSource`**：插件服务声明它（只说「按 `SecretRef` 取一条真值」），实现落在 `AppStore`——后者另持一份 `Arc<dyn SecretStore>` 句柄。读取真值发生在**配置锁之外**，投影全程不持配置锁；服务层也拿不到密钥链的写入能力。
- **解析的粒度**：取完投影快照之后、进入逐插件流程之前，只对「启用且会被投影」的 Provider 逐个解析（每个 Provider 一次 `get`）。判据与插件映射**同一条规则**：端点插值后仍非空才算配置了（空串与缺省同义，ADR 0015）——插件映射会跳过的 Provider 压根不会被投影，不该被要求提供密钥；禁用的同理（#94）。两者都不需要密钥，也不该因密钥问题阻塞「应用到工具」。
- **失败即整体失败**：任一条目不存在或密钥链不可用，整个「应用到工具」失败并点名该 Provider，不进入逐插件流程、不产生逐插件报告。两种病因分得开：「条目不存在，请重新设置」与「密钥链不可用」——处置不同，措辞也不同。错误只带 slug，不带密钥值。
- **插件仍收明文**：解析结果以「slug → 明文 / 未设置」进入插件映射，插件收到的仍是 `api_key: option<string>` 明文，WIT 合同与内置 pi 插件代码不变。`Ref` 绝不以 URI 形式进插件——插件会把 `secret://…` 当成 API Key 用。
- **旧明文照常工作**：迁移（#147）落地前，配置里的旧明文按原样投影；解析只把引用换成真值，不改写配置。

修订（2026-10-29，落地 #147）：启动时自动迁移落地，上一节末句的「解析…不改写配置」随之作废——迁移现在改写配置（明文换成引用），只有迁移失败者才仍旧以明文投影。

- **迁移的时机**：在配置存储构造时、配置解析与引用 / slug 一致性校验之后**立即执行**，早于命令与插件启动。迁移的任何失败都**不让启动失败**——密钥链不可用（如 headless Linux 没有 Secret Service）时应用照常启动。
- **逐 Provider 尽力而为**：把 `Plaintext` 写进密钥链，成功换成规范 `Ref`，失败**保留 `Plaintext`** 并记一条 ERROR（只含 slug 与原因，绝不含密钥值）。全部尝试完**只落盘一次**（成功的写引用、失败的写回明文），不一个 Provider 写一次。
- **落盘失败**：内存状态回滚为迁移前状态（配置压根没被换掉）并记 ERROR；本次已写入的密钥链条目**保留**——惰性残余，同 slug 下次写入时覆盖。
- **只在下次启动重试**：不提供手动重试命令或按钮。`Clear` 对 `Plaintext` 不需要密钥链即可清除（明文没有条目可删），`Replace` 在密钥链可用时顺带完成迁移。
- **状态可由配置直接推导**：迁移后 Provider 的三态直接由配置读出（`plaintext` 即界面上的「明文待迁移」），本票**不新增密钥链查询**。

修订（2026-10-29，落地 #148）：界面单向写入落地，前面「界面保持单向写入」一条随之成立。

- **读路径只给状态**：列表命令返回的记录里，凭证是三态词 `api_key_state`（`unset` / `set` / `plaintext`）——既不回传真值，也不回传引用 URI。状态完全由配置推导，读列表**不触发任何密钥链调用**。
- **写路径按动作走**：界面决定的是这次保存对密钥的**动作**，负载据此成形——不变（负载不带 `api_key`）、清除（`""`）、覆盖（新值）。不碰密钥时负载压根不带这个字段，后端因此一个字节都不碰密钥链。输入框里的值先去掉首尾空白：只有空白等同留空（展开后敲了个空格就保存，不会把旧密钥覆盖成空格）。
- **更换 / 清除的交互**：未设置时直接给输入框（留空即不设置）；已设置或明文态只给「更换 API Key」，展开后留空即清除。展开与否是组件本地状态（与 `enabled` 同类，不是 `Form.Item`），密钥值从不进表单状态。
- **明文待迁移的告警**：迁移失败者的状态是 `plaintext`，界面标记「明文待迁移」，并提示重启重试或重新设置。

接受的残余风险（#147 追加）：迁移在启动主线程同步做完（密钥链写 + 一次落盘），故密钥链后端挂起时会拖慢启动——迁移失败只是不迁移，不会让启动失败，但等待照样发生；条目数即 Provider 数，故耗时随 Provider 数线性增长。
