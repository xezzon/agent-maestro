# 插件以 WASM 模块作为运行时形态

Maestro 需要一个插件系统来把统一配置**投影（Projection）**到各个 Agent 工具，且内置插件与第三方插件必须走完全相同的加载路径。我们选择把每个插件编译为 WASM 模块（`wasmtime` + WASI/component model，`wit-bindgen` 生成 SDK 绑定），由 Maestro 宿主在运行时实例化。

之所以选 WASM：它是唯一能同时满足三个约束的方案——内置插件就是随包分发的一个 `.wasm`，与用户放入的第三方 `.wasm` 走同一个加载器；插件可以表达真实逻辑（各工具的配置路径、字段计算等怪癖），而非把声明式 DSL 养成一门糟糕的编程语言；第三方不可信代码运行在沙箱里——文件系统访问被 WASI 限制在宿主预授权的工具配置目录内（插件在该目录内直接写入），网络默认不可用；凭据由宿主在调用前从系统密钥链解析为明文，随统一配置一并注入插件输入。插件通过 WIT 导出 `manifest` 自描述其身份（id、适配的工具、版本），宿主加载后读取并以 tool 路由投影，不硬编码任何具体工具的语义。

## Considered Options

- **原生动态库**（`libloading` 加载 `.so`/`.dll`/`.dylib`）：放弃。不可信第三方代码无沙箱、在进程内拥有全部权限；跨 rustc 版本的 `#[repr(C)]` ABI 稳定性是长期负担。
- **子进程**（executable/脚本，stdio 上跑 JSON 协议）：次优方案。隔离性好、可跨语言，但需要为每个 OS/架构分发并签名二进制，Windows 上有杀软摩擦，脚本还依赖解释器。
- **声明式 spec**（数据文件描述路径规则 + 字段映射）：放弃。一旦某个工具（如 Pi）出现声明式无法表达的怪癖，就会抽象泄漏。
