# 0008: 日志经 tauri-plugin-log 落盘 `~/.maestro/logs`，按大小轮转、单旋钮控级

应用需要可交付的现场证据：release 下 `windows_subsystem = "windows"` 使 stderr 无处可去（`plugin/mod.rs` 仅有的 3 处 `eprintln!` 等于不存在），命令错误只在 antd `message.error` 里一闪而过，插件装载与投影全程黑箱。我们决定采用 Tauri 官方的 `tauri-plugin-log`（`log` crate 门面、fern dispatch）作为唯一日志门面，落盘 `~/.maestro/logs/agent-maestro.log`，开发期同时输出 stdout；前端经 `@tauri-apps/plugin-log`（capability `log:default`，即 `allow-log` 一条）把 `console.*` 与未捕获异常汇入同一文件。选 `log` 门面而非 `tracing` 全家桶，决定性因素是轮转能力：单文件必须有大小上限，否则插件的刷屏路径能把磁盘写爆，而 `tracing-appender` 只有时间轮转、单文件无上限。代价是 `tracing` 生态的第三方事件（wasmtime-wasi、wiggle、zbus、hyper）收不到——那是 VM 与网络内部细节，对报障定位价值低；真需要时以 `.skip_logger()` + 自建 subscriber 整体替换，是一次受控替换而非渐进腐化。落盘位置不用插件的 `LogDir` 默认（Tauri 应用数据目录），理由与 ADR 0001 偏离默认配置目录同源：用户可见、易备份、跨平台路径统一；路径由 `MaestroPaths::logs_dir()` 提供，`~/.maestro` 布局仍单点收束（#48）。文件跨启动连续追加（`FileOpenStrategy::Append`），不按会话切分——「用户报障发一份文件」不能被切成碎片。

轮转参数：`max_file_size` 1 MiB + `RotationStrategy::KeepSome(15)`，稳定态为 15 份归档 + 1 份活动，总占用约 16 MiB 封顶（归档名 `agent-maestro_<日期>_<时间>.log`）。插件的默认值一律不可用：级别默认 `Trace`、`max_file_size` 默认 40 KB、轮转默认 `KeepOne`——后者在轮转时直接 `fs::remove_file` 删掉超限那份，恰在最需要上一份证据时销毁它。时间用 UTC、行格式保留插件默认（`[日期][时间][target][LEVEL] 消息`）：正确做法是 `.timezone_strategy()` 与 `.format()` **都不调用**——`timezone_strategy()` 会重写 dispatch 的 format，把字段顺序从 `[target][LEVEL]` 变成 `[LEVEL][target]`，显式传 `UseUtc` 反而改变输出。

级别是单一全局旋钮：默认 `INFO`（开发与发布一致，不以 `debug_assertions` 区分），环境变量 `MAESTRO_LOG_LEVEL` 接受裸级别名 `error|warn|info|debug|trace` 直接覆盖，非法值忽略并在 logger 就绪后补一条 WARN。不做 per-crate 地板（`level_for`）：单旋钮意味着开 DEBUG 时第三方 crate 的 DEBUG 一并进来，「为看一条而收一片」是接受的代价；默认 INFO 下进文件的第三方 INFO 主要是 wasmtime 的编译进度行，量级为每插件装载数行。级别不写入 `config.json`——它不是领域设置，UI 侧开关归设置页（#67）。

日志是诊断设施而非运行依赖，**写不出日志绝不阻断启动**。插件的 logger 在其 setup 里 attach，而 plugin setup 发生在 `Builder::build` 阶段（tauri 2.11.5 的 `app.manager.initialize_plugins`），早于应用自己的 setup（`RuntimeRunEvent::Ready`）——启动代码的日志因此能落盘；但插件 setup 的 `Err` 会一路传播成 `build()` 的 `Err`、最终由 `main` 的 `.expect` 变成 panic：`TargetKind::Folder` 的目录创建或文件打开失败会让应用起不来。所以在注册日志插件之前先对 `logs_dir()` 做写探测（`create_dir_all` + 以 append/create 打开日志文件），失败则只装 Stdout target、应用照常启动，等 logger 就绪后在 setup 里补一条 WARN（release 的 GUI 下不可见，第一期接受）。这条与既有姿态一致：插件服务在 `~` 不可用时退化为命令层报错，从不拖垮启动。

埋点集中在命令层与服务层。命令层经 `command/mod.rs` 的 `log_outcome` 输出「结果行」：成功 INFO 携带识别参数（slug/source），失败 ERROR 携带原因；含网络下载的安装类命令（`add_plugin`/`reload_plugin`）另加进入行——「有进入、无结果」正是定位卡住（如 #46 的 AppImage 场景）的证据；`apply_providers` 的结果行携带逐插件状态摘要。服务层（fetch / 校验 / 落位 / 投影各步骤）打 DEBUG，默认级别下不落盘，供复现时用 `MAESTRO_LOG_LEVEL=debug` 展开。`plugin/mod.rs` 启动路径的 3 处 `eprintln!` 转为 `warn!`/`error!`，启动完成打一条 INFO（providers/plugins 计数）。配置存储锁毒化的因果链无需额外代码即闭环：持锁期间的 panic 由 panic hook 记录，后续命令的「配置存储不可用」ERROR 紧随其后。我们自己书写的日志行用英文（日志是给 grep 与工具读的）；错误原因沿用现有中文用户可见文案，国际化（#68）落地后随 UI 文案统一。

凭证绝不落盘是本设施的硬约束，且日志抬高了秘密的风险量级：配置文件里本就有明文 `api_key`（ADR 0002 现状态），而日志是**第二份持久副本**、且是明确鼓励「发给维护者」的一份。落法：`Provider` 手工实现 `Debug`（`Config` 的派生 `Debug` 内层调用它，因此同获保护），`api_key` 渲染为 `<set>`/`<unset>`——既不泄密又保留「配没配 key」这一排障高频信息；命令 payload（`ProviderRequest` 携带明文 key）绝不进日志，日志只打识别参数；`base_url` 允许出现（端点是排障高频信息），用户把凭证写进 userinfo 时会随之进日志，记为已知取舍。验证分两层：L1 单元断言 `format!("{:?}", provider)` 不含密钥；L2 金丝雀——测试内安装捕获 logger，以带唯一 canary key 的 provider 跑真实投影路径，断言全部捕获输出不含该值（与 `LockProbeFetcher` 用替身钉住「拉取不得持锁」是同一属类：把不变量变成可执行断言）。已知的残余风险接受并记录：`StoreError::Corrupt` 的 serde 错误串在极端情况下携带出错位置的原文片段（用户把密钥贴进结构上错误的字段时才会发生）；插件在自己的错误消息里回显密钥（它本就持有该秘密）。均不以机制防御，`Secret` newtype 之类的包装对第一期是过度设计；前端整包转发 `console.*` 带来的「开发者打印凭证即落盘」路径同类（见末两段）。

未捕获 panic 由自装 hook 兜住（tauri-plugin-log 不装 panic hook）：在 `run()` 中 `builder.run(...)` 之前 `std::panic::set_hook`，并以 `take_hook()` 取出原 hook 链式调用，保住 stderr 默认行为；logger attach 之前的 panic 仍由原 hook 打到 stderr。这条的价值在命令 panic：IPC 调用永不返回、前端 promise 挂住，而日志里留下 panic 的 file:line 与消息。前端整包转发 `console.*`（按 `@tauri-apps/plugin-log` 官方示例的级别映射：`log`→`trace`、`debug`→`debug`、`info`→`info`、`warn`→`warn`、`error`→`error`；原生输出保留），另加 `window.addEventListener` 的 `error` 与 `unhandledrejection` 两个监听把未捕获异常交给 `error()`（记录 target 为 `webview::<location>`）——浏览器对未捕获错误的内部报告不走 console 对象，转发覆盖不到它。两个入口的参数都可能是对象或循环引用，须经安全格式化：`JSON.stringify` 对 `undefined` 与函数返回 `undefined`，须回落 `String()`，循环引用以 try/catch 兜住，防止兜底处理器自己抛出；plugin-log 只接受 string，非字符串参数必须字符串化，否则 invoke 直接拒绝。转发与两个监听都返回 promise，落盘失败一律就地吞掉——未处理拒绝会再次进入 `unhandledrejection` 监听、反复调用同一个正在失败的 logger。命令失败不从前端重复记录——Rust 命令层已经记了。整包转发是本 ADR 初版明确否决过的形态（理由「噪音控制，且 `console.log(provider)` 会把 key 写进文件」），现改为接受：噪音由级别承担——`Builder::level` 作用于整个 dispatch、先于 target，默认 INFO 下 `log`/`debug` 两条通道根本到不了落盘，`console.log` 的对象转储不会进文件；代价是 `console.info/warn/error` 会原样落盘，等于多一条「开发者打印凭证即写进文件」的路径，与 `base_url` userinfo 同属已知残余风险，不以机制拦截（日志文件本就按「发给维护者」的定位处理）。

曾考虑并否决的形态：`tracing` + `tracing-subscriber` + `tracing-appender` 自建（`EnvFilter` 与双生态覆盖更强，但轮转只能按时间、单文件无大小上限，前端桥也要自写，约 60 行模块 + 4 个 crate）；`level_for` 做 per-crate 地板（须为 `webview` 前缀单开口子，否则前端日志被地板挡掉——单旋钮下该坑消失，复杂度不值）；复用 `RUST_LOG`（没有 EnvFilter，假装支持 `module=level` 指令只会静默误解析）；`TargetKind::Webview` 把 Rust 日志镜像进 webview 控制台（每条记录 spawn 一次异步任务，仅开发期有意义）；`KeepAll`（归档份数无界）与 `KeepOne`（轮转即删除超限份）；显式 `.timezone_strategy(UseUtc)`（重写 format、颠倒字段顺序）；按会话分文件（把证据切碎）；`Secret<String>` newtype（第一期过度设计）；UI 入口「打开日志目录」（前端尚未用过 opener 插件，需新增 reveal 本机路径的权限，且位置与 #67 设置页强耦合，挪入该 issue）；WASM guest 日志通道（stdout/stderr 接线会改变 guest 行为——现在写 stdout 落到未接线的 fd 上会失败；WIT `log` 函数是对外公共接口的版本成本；受众是插件作者而非报障用户，单开 issue）。
