# 0003: Provider 协议分槽建模（`base_url` 按协议分槽、共享凭证与模型）

Provider 用不同线协议与 LLM API 对话，而一个上游（如公司网关）可能在同一个凭证下同时暴露 OpenAI 兼容与 Anthropic Messages 两类端点。我们决定：协议为枚举（`openai-completions` / `anthropic-messages`），Provider 的 `base_url` 是一个按协议分槽的 map（每协议至多一个端点，未配置的协议不写入 JSON——键缺省而非空串），一份 `api_key` 与一份模型列表跨协议共享。「键缺省即未配置」这一不变量由写入侧保证——空串不是合法端点，未配置的槽不写入文件；读取侧只忠实还原文件内容：键缺失视为未配置，显式空串原样保留为 `Some("")`，不做归一化，已有配置无需迁移。

这使「一条 Provider = 一个上游 + 一份凭证」的领域语义成立：双协议只是同一上游的两个入口。本期界面用单选框强制二选一、只填一个槽位，但 schema 从第一天就允许双端点，将来放开时无需数据迁移。曾考虑「协议 + base_url 两个平铺标量字段」——更简单，但同一 Provider 未来要支持第二种协议时必须迁移数据结构，故弃用。

修订（2026-09-06）：撤销首版「读取侧把显式空串同样归一化为未配置」的兼容层。它防御的输入本应用的写入路径不会产生（写侧已保证键缺省，界面也校验 Base URL 必填且为合法 URL），代价却是每个槽位挂一个自定义反序列化器，且让读取结果偏离文件原文；删除后读取如实反映文件内容，空串是否有语义交由领域层后续决定。
