# 0003: Provider 协议分槽建模（`base_url` 按协议分槽、共享凭证与模型）

Provider 用不同线协议与 LLM API 对话，而一个上游（如公司网关）可能在同一个凭证下同时暴露 OpenAI 兼容与 Anthropic Messages 两类端点。我们决定：协议为枚举（`openai-completions` / `anthropic-messages`），Provider 的 `base_url` 是一个按协议分槽的 map（每协议至多一个端点，未配置的协议不写入 JSON——键缺省而非空串），一份 `api_key` 与一份模型列表跨协议共享。空串不是合法端点，把未配置的槽写进文件只会制造「已配置但为空」的歧义；键缺省即未配置，读取侧对键缺失与显式空串同样视为未配置，已有配置无需迁移。

这使「一条 Provider = 一个上游 + 一份凭证」的领域语义成立：双协议只是同一上游的两个入口。本期界面用单选框强制二选一、只填一个槽位，但 schema 从第一天就允许双端点，将来放开时无需数据迁移。曾考虑「协议 + base_url 两个平铺标量字段」——更简单，但同一 Provider 未来要支持第二种协议时必须迁移数据结构，故弃用。
