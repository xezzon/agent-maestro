# 0021: 只讲一种线协议的工具，端点协议由工具决定

ADR 0016 把「投影用哪个端点」判给插件，并写下一套选择规则：所选协议确有对应端点则用它；否则若只剩一个端点则用它；否则多端点且无有效选择时优先 `openai-completions`。ADR 0016 同时明确**合同只约束输入的形状，不约束选择策略**——但那套规则在它的正文、`docs/GLOSSARY.md` 的「端点」条目与 `plugins/pi/README.md` 里都被写成了通则。照抄这条通则去适配只讲一种线协议的工具，会得到一个打不通的端点。

Claude Code 只能对接 Anthropic Messages：它把 `ANTHROPIC_BASE_URL` 当作**基址**、自行追加 `/v1/messages`。对一条两种端点都配了的 Provider，按上面的兜底链会选中 `openai-completions` 端点，把它写进 `ANTHROPIC_BASE_URL` 必然不通。

我们决定：**目标工具只支持一种线协议时，协议由工具本身决定**——插件直接从 Provider 的端点里取该协议的端点，既不套用 ADR 0016 的兜底链，也不看 `selected_protocol`（界面记录的投影选择）。不看 `selected_protocol` 的理由是它是 **Provider 级**、被所有插件共用的记录：把它当过滤器，用户就被迫在工具之间二选一（把该 Provider 的选择设成 `openai-completions` 才能让某类工具满意，另一类工具却因此完全看不到这条接入）。而取该协议端点是唯一能让这类工具工作的选择；每协议至多一个端点，因此**这里根本不存在需要兜底的取舍**。

代价与义务：这类插件的候选集合是「配了该协议端点的 Provider」，其选择策略必须**写下**（写在该插件的 README，参照 `plugins/pi/README.md`）；`docs/GLOSSARY.md` 的「端点」条目补一句限定，免得通则继续误导后来者。本限定只对「工具只讲一种协议」成立；pi 这类可在两种协议间选择的工具仍按 ADR 0016 的链走。本次不改 WIT 合同——`selected_protocol` 照旧交付，只是这类插件不读它。

曾考虑并否决的形态：**照抄兜底链、结果不是该协议的 Provider 就跳过**（两种端点都配且未记录选择——最常见的形态——对这类工具会全部不可见）；**把 `selected_protocol` 当过滤器**（见上，迫使用户在工具之间二选一）；**由 Maestro 表达「某条接入供哪些工具使用」**（把工具专有的选择知识放进领域模型，与 ADR 0016 的分工相抵，也与 ADR 0020 的结论冲突）。
