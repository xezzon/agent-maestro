# 0012: 应用版本号单一来源为 tauri.conf.json

应用版本号原本同时写在四处：`package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 与 `src-tauri/Cargo.lock`，每次发版逐处同步，其中 lock 是否与 manifest 同拍只能靠 `cargo metadata --locked` 反查。四处里真正被读到的只有两处：发布侧的 tag 与产物版本、运行时的 `PackageInfo` 都取自 config（tauri-action 与 tauri-codegen 都先读 config 的 `version`，缺失才回退 Cargo 清单），`src-tauri/src/plugin/fetch.rs` 的 User-Agent 经 `CARGO_PKG_VERSION` 读到 Cargo 清单那份，`package.json` 的版本在本仓库没有任何读取点。另一项代价此前没有计入：Cargo 会把本地包自己的版本写进 `Cargo.lock`，于是每次发版都改 lock，而两条工作流的四个缓存键都含 `hashFiles('**/Cargo.lock')`（见 [0009](0009-manual-release-and-per-profile-cache.md)）——**每次发布都在轮换全部缓存键**，在仓库 10 GB 配额下不断新建条目、加速 LRU 驱逐，与 0009 压缩缓存的初衷相抵。

决策是：应用版本号的唯一来源为 `src-tauri/tauri.conf.json`，其余三处一律不再持有。Cargo 清单直接省略 `[package] version`（该字段自 Cargo 1.75 起可选，省略即按 `0.0.0` 处理；本 crate 已有 `publish = false`，省略还是 Cargo 文档推荐的防误发布手段；实测 cargo 1.98 下 `cargo metadata` 与代码里的 `CARGO_PKG_VERSION` 都得到 `0.0.0`）；`package.json` 删除顶层 `version`（npm 不要求不发布的包带它，本包 `private: true` 且全仓库无读取点；实测 `pnpm install --frozen-lockfile` 照常通过）；`src-tauri/Cargo.lock` 里 `agent-maestro` 随之固定为 `0.0.0`，此后不随发版变动（本次改动后 lock 的差异就只有这一行）。发版动作因此收缩为改一行 `src-tauri/tauri.conf.json`，`cargo metadata --locked` 这一步也随 lock 一致性问题的消失而退出流程（`.agents/skills/bump-version/SKILL.md` 已同步）。

被 `CARGO_PKG_VERSION` 读到的那个 UA（`agent-maestro/<version>`）改由 `src-tauri/build.rs` 在构建时读同一份 config 注入 `AGENT_MAESTRO_APP_VERSION`；为此 `serde_json` 进入 `[build-dependencies]`，它本就在依赖图里，lock 不新增条目。config 读不到、不是合法 JSON 或没有 `version` 字段时构建直接失败，而不是让 UA 静默退化成 `0.0.0`。发布侧的写入也随之交给工作流：`.github/workflows/release.yml` 新增一个 bump job，把 dispatch 的 `version` 输入写进这个文件、提交并推送 main，release job 在该提交上构建，tauri-action 的 tag 也落在这个提交上（`releaseCommitish`）；原先「输入必须等于 config 版本」的校验 step 就此删除——输入不再需要核对，它就是被写入的值。

曾考虑并否决的形态：运行时改读 `app.package_info().version`。它的值同样来自 config，但要把版本一路传进 `src-tauri/src/plugin/fetch.rs`——该模块是 0006 定义的纯 https 缝，刻意不依赖 Tauri、测试以替身注入——于是 `HttpFetcher::new`/`PluginService::new` 的签名与若干调用点、测试都要跟着改，换来的只是同一份 config 的另一种读法；更关键的是失败模式：config 缺 `version` 时 tauri-codegen 会回退 `CARGO_PKG_VERSION`，在 Cargo 清单也不再持有版本之后就变成静默的 `0.0.0`，而 build.rs 注入在缺字段时是构建期直接失败。运行时方案唯一的优势是能采纳 `tauri build --config` 的版本覆盖（codegen 用的是合并后的配置），本仓库的发布流程不使用该覆盖，故不取。也考虑过把版本留在 `Cargo.toml`、反向从 config 删除，但那样每次发版仍要改 `Cargo.lock`、缓存键照旧轮换，等于保留本次要消除的那项代价。

发布侧与运行时的取值优先级已按源码核对：tauri-action v1 的 `src/utils.ts` 中 `getInfo` 先取 `config.version`（并支持把它写成指向某个 package.json 的路径），仅在 `if (!(name && version))` 时回退 `Cargo.toml` 的 `package.version`；tauri-codegen 的 `context.rs` 同样只在 `config.version` 为空时才用 `env!("CARGO_PKG_VERSION")`——这两处正是本次改动的两个消费者，config 保留 `version` 即不受影响。尚未实跑验证的点：缓存键不再轮换带来的命中率变化要等下一次发布在 CI 上观察（本次改动本身会让四个键各轮换一次，因为 lock 变了）；本地只验到 Linux 的 debug 构建（build script 的 `output` 里出现 `AGENT_MAESTRO_APP_VERSION=0.4.0`、二进制内 UA 仍是 `agent-maestro/0.4.0`），Windows/macOS 打包产物里的版本元数据未验证。
