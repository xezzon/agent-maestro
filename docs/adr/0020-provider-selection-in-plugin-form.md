# 0020: 单一端点工具的 Provider 选择由插件表单承载

Maestro 允许并存任意多条 Provider（各自的 slug、端点、凭证、模型），宿主投影时把**全部已启用**的 Provider 一次性交给每个插件，由插件裁定用哪个端点（ADR 0016）、字段重叠时用哪个字段（ADR 0019）。这套分工有一个隐含前提：目标工具在配置里能**并列容纳多条接入**。pi 的 `models.json` 按 slug 并列、工具自带选择器，前提成立。

但不是每类工具都如此。Claude Code 只用一组环境变量指向单一 API 端点与单份凭证，同时只能对接一条接入。于是「宿主交出全部 Provider」在这里第一次产生了 Maestro 从未回答过的问题——**该用哪一条**？这个问题的答案不属于 Maestro 的通用模型：它是「某类工具怎么挑接入」的知识，与「哪种协议更适合某类工具」同源，而后者已按 ADR 0016 判给插件。

我们决定：**由该工具的插件在自己的插件表单里承载这个选择**（ADR 0017 的 `settings_schema` 与 ADR 0018 的 `form`），放置一个可选的 Provider slug 字段。填了就投影它；留空则按确定性规则兜底——候选恰好一条就用它，零条则清空本插件维护的键（视为成功），多于一条则本次投影失败并列出候选、由用户来选。规则由插件自己实现并**写下**（ADR 0019 的姿态），Maestro 只负责记录与交付，不引入任何全局状态。ADR 0017 早已以「Claude Code 要选定单一 model」为例说明表单是为这类工具专有项准备的，Provider 选择只是同一机制下的另一个字段。

这样同一份 Provider 集合可以同时服务偏好不同的多类工具：pi 把全部接入并列进去，Claude Code 只取表单点名的那一条。**「一条 Provider 级的选择无法同时服务两个工具」**正是这里不能把选择上收进 Maestro 的理由——同一个网关的 `openai-completions` 端点可能对某类工具更好，而 `anthropic-messages` 端点才是另一类工具唯一可用的。

曾考虑并否决的形态：**Maestro 侧引入全局「当前 Provider」**（store 加字段、加界面、改变投影交付语义，属横切特性；且它只能表达「一条」，一旦两类工具各自需要不同的接入就又不够，等于把工具专有的选择硬塞进领域模型）；**宿主在投影前按工具过滤 Provider**（宿主随即必须知道「哪类工具要哪种协议、要几条接入」，正是 ADR 0016 从宿主移走的那类知识）；**插件自由挑选、不报错**（多候选时静默取首个或字典序首项，用户会把配置错误当成工具故障）。
