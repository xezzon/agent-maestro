# 0006: 第三方插件来源为 https URL 与本地路径，产物经 GitHub Release 分发

第三方插件（见 ADR 0004）最初设计为从 Git 仓库克隆安装（git2，匿名 HTTPS、默认分支、repo 根即插件根）。现决定废弃 Git 来源，来源模型为三种：内置于应用（`builtin:<id>`）、一个指向 manifest.json 的 https URL、一个指向 manifest.json 的本机绝对路径。https 来源面向正式发布：产物（manifest.json + wasm）经 GitHub Release 分发——作者打 tag 后由 Action 锁定工具链构建 wasm、把 entry 重写为 Release 资产 URL，两文件以 `plugin.wasm` 与 `manifest.json` 挂上 Release；发布点不可变（发新版 = 打新 tag，发布版 manifest 不回写仓库），宿主不感知 GitHub，只做纯 https 下载。file 来源面向插件作者的本地开发回路：从本机目录直读装载，不复制、不落位。放弃 Git 的理由：克隆管线与 git2 依赖只为「拿到一个目录」，却引入仓库默认分支漂移、无不可变发布点、第三方产物被迫入库（或 bot commit 产物流）三个问题；显式发布流让 ADR 0005 的「产物不入库」哲学自然延伸到第三方插件。来源 URL 仅接受 https（明文 http 拒绝，本地调试有 file 来源兜底）；source 字符串原样存储为条目身份、重复添加按精确匹配在 store 层拒绝，不做 realpath/符号链接归一化。

entry 语义按来源分列，不做跨协议的统一解析：https 来源的 manifest，entry 必须是 https URL；file 来源的 manifest，entry 是相对 manifest.json 所在目录的相对路径或 https URL；绝对路径与 `..` 一律拒绝——ADR 0004 的反逃逸性质完整保留，任何 manifest 都不能让宿主读插件根之外的文件；builtin 插件 wasm 内嵌，entry 不参与解析。装载模型：https 来源沿用 0004 的落位语义——下载 manifest 与 wasm 后落位 `~/.maestro/plugins/<id>/`（落位时 entry 重写为本地相对名 `plugin.wasm`，磁盘 manifest 因此 ≠ 上游 manifest，仅此一处），应用启动只读磁盘、离线可用，生命周期（添加先写条目、失败进错误态；更新重新下载、成功才替换、上游 id 变更报错保持旧状态；重新加载只读落位目录；移除幂等）逐条沿用；file 来源不落位，entry 为相对路径时读本机文件，为 https URL 时装载即联网获取且不缓存（离线进错误态，联网后「重新加载」即恢复），无「更新」操作、「重新加载」即取最新。仓库内 manifest.json 的 entry 指向 cargo 原生产物路径（`target/wasm32-wasip2/release/<crate>.wasm`），本地构建后即存在，开发回路「编译 → 重新加载」零拷贝。信任模型不变：安装即信任，与自装 npm 包同级，沙箱隔离能力滥用、不审查内容。

曾考虑并否决的形态：保留 Git 来源与其 bot commit 产物流（原 0004 设计与 issue #36 原方案，理由见上——显式发布流使产物入库与机器人回写都成为多余环节）；统一 entry 语法为 RFC 3986 相对引用、两种协议共用一套解析（更通用，但 https 来源的相对 entry 只服务「同目录扔静态服务器」的边缘场景，且扩大校验面，按协议分列从严）；明文 http 来源（信任模型虽是安装即信任，正式渠道的可执行代码下载没有理由不走加密通道）；file 来源 https entry 的 wasm 缓存（为开发者模式的离线边缘场景引入缓存失效与「重新加载」语义分叉，不值）；落位时保留上游 entry、装载时做 URL→本地文件的隐式映射（不如直接重写 entry 诚实）；落位 manifest 的 entry 指向 URL 末段文件名（固定名 `plugin.wasm` 更简单且不受 URL 形态影响）。
