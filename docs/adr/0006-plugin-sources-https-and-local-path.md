# 0006: 第三方插件来源为 https URL 与本地路径，产物经 GitHub Release 分发

第三方插件（见 ADR 0004）最初设计为从 Git 仓库克隆安装（git2，匿名 HTTPS、默认分支、repo 根即插件根）。现决定废弃 Git 来源，来源模型为三种：内置于应用（`builtin:<id>`）、一个指向 manifest.json 的 https URL、一个指向 manifest.json 的本机绝对路径。https 来源面向正式发布：产物（manifest.json + wasm）经 GitHub Release 分发——作者打 tag 后由 Action 锁定工具链构建 wasm、把发布清单的 entry 指到 Release 资产 URL，两文件以 `plugin.wasm` 与 `manifest.json` 挂上 Release；发布点不可变（发新版 = 打新 tag，发布版 manifest 不回写仓库），宿主不感知 GitHub，只做纯 https 下载。file 来源面向插件作者的本地开发回路：添加与重新加载时读来源目录的 manifest.json，并按其 entry 取 wasm（相对路径读来源目录内文件，https URL 则联网获取），一并落位到 `~/.maestro/plugins/<id>/`，之后与 https 来源同构（见下）。放弃 Git 的理由：克隆管线与 git2 依赖只为「拿到一个目录」，却引入仓库默认分支漂移、无不可变发布点、第三方产物被迫入库（或 bot commit 产物流）三个问题；显式发布流让 ADR 0005 的「产物不入库」哲学自然延伸到第三方插件。来源 URL 仅接受 https（明文 http 拒绝，本地调试有 file 来源兜底）；source 字符串原样存储为条目身份、重复添加按精确匹配在 store 层拒绝，不做 realpath/符号链接归一化。

entry 语义按来源分列，不做跨协议的统一解析：https 来源的 manifest，entry 必须是 https URL；file 来源的 manifest，entry 是相对 manifest.json 所在目录的相对路径或 https URL；绝对路径与 `..` 一律拒绝——ADR 0004 的反逃逸性质完整保留，任何 manifest 都不能让宿主读插件根之外的文件；builtin 插件 wasm 内嵌，entry 不参与解析。entry 是「回源地址」：重新加载（见下）时据此知道从何处重新获取 wasm。

装载与落位模型：第三方来源（https 与 file）统一落位 `~/.maestro/plugins/<id>/`，仅两文件——`manifest.json` 原样保留上游内容（entry 仍是回源地址，不重写），wasm 内容固定存为 `plugin.wasm`。配置条目的 `id` 在安装成功时写入、是来源到落位目录的唯一映射（启动时据此定位目录，插件 id 与来源的对应关系不另存一份）。应用启动只读落位目录重建注册表：manifest 提供 metadata（id/name/tool/config_dir），wasm 固定读 `plugin.wasm`、不解析 entry，因此离线可用。生命周期：「添加」先写条目、随后获取 manifest 与 wasm、失败进错误态并保留条目；「重新加载」按配置中的来源重新获取 manifest 与 wasm，成功才替换落位目录、失败时旧版本保持可用，上游 id 变更报错并保持旧状态；不存在「一次重载所有插件」的操作，重新加载必须指明某个来源；「移除」删条目与落位副本且幂等。file 来源与 https 同构地落位与重新加载，区别仅在获取方式：entry 为相对路径时从来源目录读 wasm，为 https URL 时从网络获取；移除只删条目与落位副本，不动用户项目目录。仓库内 manifest.json 的 entry 指向 cargo 原生产物路径（`target/wasm32-wasip2/release/<crate>.wasm`），开发回路「编译 → 重新加载」即把最新产物复制进落位目录。信任模型不变：安装即信任，与自装 npm 包同级，沙箱隔离能力滥用、不审查内容。

曾考虑并否决的形态：保留 Git 来源与其 bot commit 产物流（原 0004 设计与 issue #36 原方案，理由见上——显式发布流使产物入库与机器人回写都成为多余环节）；统一 entry 语法为 RFC 3986 相对引用、两种协议共用一套解析（更通用，但 https 来源的相对 entry 只服务「同目录扔静态服务器」的边缘场景，且扩大校验面，按协议分列从严）；明文 http 来源（信任模型虽是安装即信任，正式渠道的可执行代码下载没有理由不走加密通道）；落位时把 entry 重写为本地相对名 `plugin.wasm`（原决定：让磁盘 manifest 与磁盘内容自洽——但会丢失「回源地址」，而 entry 的意义正是重新加载时知道从何处重新获取资源，故改为原样保留上游 manifest，本地 wasm 名与 entry 解耦，装载只认固定名）；落位 manifest 的 entry 指向 URL 末段文件名（固定名 `plugin.wasm` 更简单且不受 URL 形态影响）；file 来源不落位、直读本机文件（原决定：省一份副本、开发回路零拷贝——但使 file 与 https 的装载路径分叉、且「重新加载」语义不一致，故改为复制落位，代价是每个插件占用一份副本）；file 来源 https entry 的 wasm 缓存（为开发者模式的离线边缘场景引入缓存失效与「重新加载」语义分叉，不值）。
