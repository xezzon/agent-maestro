# 0022: manifest 解析只产出声明，解析成路径是显式的一步

插件的 `config_dir` 声明此前在**反序列化**里就解析成宿主绝对路径并建出目录（见 ADR 0011）：`Manifest` 一经构造，`config_dir` 就是可用的路径，解析与建目录被藏进了「读一份 JSON」这个动作里。这条边界有三个具体后果。其一，解析看起来是纯函数，实际依赖全局路径单例并修改文件系统——调用顺序因此被迫敏感：安装流程里的「解析 → id 冲突检查 → 校验 → 落位」中，目录在冲突检查与校验**之前**就建好了，wasm 不合法、id 冲突、落位失败时，用户主目录下已经留下一个空目录。其二，同一份 manifest 在一次安装里被解析两遍：来源侧解析一次拿到 `entry` 与 `id`，落位产物再解析一次（两次建目录、两次规范化，之间目录若变化则两次结果不一致）。其三，接口看不出副作用——`parse_manifest` 的签名不提示它会建目录，调用方也就无从安排顺序。

我们决定把「解析」与「解析成路径」分开：**反序列化只产出声明**，声明的形态（变量前缀受支持、相对片段非空且不含绝对路径 / `..` / 裸 `.`）在解析期以纯判断校验——不读目录、不碰文件系统；「落到哪个目录」由一个**显式**的解析步骤完成：查基准目录 → 建目录 → 规范化 → 逃逸校验，返回宿主绝对路径。声明因此有两种形态且只有一种状态：`Manifest` 持有**声明**（`DeclaredConfigDir`），装载后的插件（`LoadedPlugin`）持有**解析结果**（宿主绝对路径），两者分开存放，不存在「已解析 / 未解析」并存于同一字段的情况。

顺序随之固定：**解析 → id 冲突检查 → 链接期校验 → 解析配置目录（建目录在此发生）→ 落位**（wasm 的获取在解析之后、id 冲突检查之前——冲突检查要读 manifest 才知道插件的 id，而 wasm 要按 manifest 的 `entry` 取）。建目录因此只在「wasm 确实是合法组件、id 确实没被占用」之后发生；安装失败不留配置目录。链接期校验的对象是 wasm 字节，与「插件是否已装载」无关，故它不挂在已装载的插件上，而是一个独立入口——装配方要在建目录之前问一句「这份 wasm 是不是合法组件」，不必先建出目录来。启动时从落位目录重建注册表这条路径同样解析并建目录，但那是**显式的装载步骤**，不是反序列化的副作用。

曾考虑并否决的形态：**解析期保留全部校验、只在之后建目录**（把「解析成路径」拆成「校验」与「建目录」两步）——校验要判「相对片段是否逃出基准目录」就得知道基准目录在哪，而基准目录来自全局路径单例，于是解析又会依赖全局；把「不受支持的变量前缀」这类判断留给解析期、把「逃逸」留给落位期，则两处各判一半，错误信息与失败时机都不再统一。**解析期完全不校验声明**（一切留给解析成路径那一步）——最简单，但 manifest 不合法时也要先下载 wasm 才被拒，白花一次网络往返。**保留全局路径单例但让解析读它**——解析一个来自网络的 manifest 就能读到宿主目录布局，解析不再是可独立测试的纯函数。**把解析成路径的结果缓存进 `Manifest`**（即解析期就解析，但把建目录挪走）——「声明」与「路径」两种形态又回到同一类型里，两种状态并存的坑原地复现。

后果：插件的安装与重载各解析一次 manifest（此前两遍）；安装失败（wasm 不合法 / id 冲突 / 落位失败）不再在用户主目录下留下配置目录；`config_dir` 的声明语法仍归 `plugin/manifest.rs`（ADR 0011），「平台变量前缀落在哪个目录」归 `crate::paths`——两者合成一处后，`config_dir` 声明不再由两个各自初始化的全局单例共同支撑（见 #136 P0-2）。
